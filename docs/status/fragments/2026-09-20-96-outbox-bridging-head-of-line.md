## (a) Proposed "Recently shipped" row

| 2026-09-20 | Slice 3 of `#96`: two more real subsystems bridged into the operational-event outbox, and opt-in head-of-line blocking per workflow. **Policy decisions:** every `PolicyDecision` strategy-admission policy evaluation produces is bridged by `PolicyDecisionOperationalEventBridge` into an `AUDIT` envelope (`dataloom.policy.decision.allowed`/`denied`/`user_action_required`/`deferred`, id `policy.decision.<policySetId>.<executionId>`, correlation/trace/tenant from the execution context, workflow from the request), opt-in via `DataLoomBuilder.policyDecisionOperationalEventOutboxConfiguration(DataLoomPolicyDecisionOperationalEventOutboxSpec)`, hooked in `StrategySynchronizationExecutionCoordinator` after admission and the per-execution log commit are already decided, swallowed-failure posture as the other bridges; no effect without `strategyAdmissionPolicyConfiguration`, independent of that spec's decision log; the caller-supplied `justification` is classified `CONFIDENTIAL` (removed) and check metadata is never read. **Queue-worker wake-up scheduling:** each run's `QueueWorkerSchedulingResult` other than `NotRequired` is bridged by `QueueWorkerSchedulingOperationalEventBridge` into a `SYSTEM` envelope (`dataloom.scheduler.wakeup.scheduled`/`not_configured`/`failed`/`circuit_rejected`, with closed circuit-outcome attributes and an error's closed vocabulary only), id `scheduler.wakeup.<leaseId>` (a run's lease id is unique; the reused `ScheduleId` cannot be the identity), opt-in via `DataLoomBuilder.queueWorkerSchedulingOperationalEventOutboxConfiguration(DataLoomQueueWorkerSchedulingOperationalEventOutboxSpec)`, attached by wrapping the worker `build()` returns (direct and circuit-aware) so no coordinator changed and the run result is returned unchanged. **Deliberately not bridged, with evidence:** configuration history (`DurableConfigurationHistory` has no runtime caller that records a version, so there is no event to bridge and none was invented); other scheduler events (a synchronization retry's scheduling is already the bridged `RetryScheduled` event, and nothing else in the runtime calls the scheduler or `cancel`); the plugin engine and assets (owned elsewhere). **Head-of-line blocking:** `DurableOperationalEventOutboxProcessor.process` takes `ordering: OperationalEventOutboxOrderingPolicy` (default `PRESENTATION_ORDER_ONLY`, behavior unchanged); with `BLOCK_WORKFLOW_ON_UNFINISHED_ENTRY`, once a workflow-carrying entry is left pending by the cycle (handler `Skipped`/`Failed`, or `Processed` with a failed acknowledgement) none of that workflow's later entries is handed to the handler, while other workflows keep flowing; blocked entries stay pending untouched, are reported in a new `OperationalEventOutboxProcessingSummary.blocked` counter, and do not count toward `maxEntries`; the hold persists across cycles with no extra state (a pending entry is always presented before its successors) and releases in the same cycle when the blocker is now processed-and-acknowledged, or the next cycle when someone else acknowledged it. Documented decisions: workflow-less entries neither block nor are blocked; a filter-rejected entry does not block; per processor call, not a distributed lock. **Verified:** on the Windows JVM (exit code 0), the targeted suites `DurableOperationalEventOutboxProcessorTest` (10 new head-of-line tests: default unchanged, interleaved workflows, skipped and failed, hold across cycles then in-order release, external acknowledgement release, `maxEntries` accounting, acknowledgement failure, workflow-less, filter-rejected, summary counter), `PolicyAndSchedulerOperationalEventBridgesTest` (pure mapping tables over every outcome and circuit variant, id sanitisation, redaction of justification/error message, idempotence), `DataLoomBuilderStrategyAdmissionPolicyTest` (5 new: allow/deny bridged without a decision log, append failure never changes admission, nothing without policy or without outbox) and `DataLoomBuilderQueueLifecycleOperationalEventOutboxTest` (4 new through a real built worker: wake-up bridged, nothing when not required, append failure never changes the result, no effect without a worker); full module runs, both ABI layouts and iOS cross-compile are listed in the PR body. **Not verified:** Kotlin/Native execution of the new tests (cross-compiled only); the circuit-aware scheduling wrapper through a real `DataLoomBuilder` (covered only by the pure bridge tables); a real scheduler-provider `Scheduled` result end to end (the builder tests exercise `SchedulerNotConfigured`). See `docs/api/operational-envelope-redaction.md` (`#96`, 2026-09-20) | `#96` feature |
