# Fragment: `#97` file-backed asset providers keep their committed index across a restart (2026-10-05)

For the lead to fold into `docs/status/market-readiness.md`. Not edited by this PR itself.

## (a) Proposed "Recently shipped" row

| 2026-10-05 | `#97`: **closes a real gap under the "file-backed restart-recovery evidence" claim.** `FileAssetProvider` (JVM) and `AppleFileAssetProvider` kept the committed-asset index only in memory: bytes survived under `committed/<id>/<version>/asset.bin`, but a fresh instance over the same directory answered `ASSET_NOT_FOUND` for everything previously committed (the manifest and per-chunk stored offsets were never persisted). Now `completeUpload` writes a small versioned `manifest.dlc` (new `internal` `CommittedAssetRecordCodec` in `commonMain`: header/version, per-chunk *stored* lengths, one manifest via the existing `AssetManifestHistoryStateCodec`) beside `asset.bin` with the same temp-then-rename discipline, after the asset file is promoted (the manifest is the commit marker; a stale manifest is removed first; a manifest-write failure removes the new `asset.bin` and returns `PROVIDER_REJECTED`). The index is rebuilt lazily on the first operation of an instance, under the existing mutex (construction stays I/O-free; a failing listing is a typed result and is retried). Fail-closed: an entry is indexed only if the record decodes under the real manifest invariants, directory names match the manifest's asset id and version, and `asset.bin`'s size equals the recorded stored lengths; otherwise it is skipped (counted in an internal `skippedCommittedEntryCount`), never served, and a re-upload of that id/version replaces it. The scan does not re-hash whole objects; instead `readChunk` now verifies each untransformed chunk against its manifest digest before returning it (same-size bit rot gives `OBJECT_DIGEST_MISMATCH`); transformed frames stay the client's authenticated-decryption check. In-flight uploads are still not recovered and not exposed. No public API/ABI change (ABI baselines untouched). Verified on Windows: `:dataloom-assets:jvmTest --rerun-tasks` (290 tests, 0 failures; 14 new: 12 in `FileAssetProviderRestartTest` over real temp directories -- round trip byte-identical and digest-verified, multi-asset/multi-version with latest-version resolution, version-conflict and quota enforced from the recovered index, compressed+encrypted asset uploaded and downloaded through `AssetTransferEngine` by a fresh provider, in-flight upload not exposed, corrupt manifest, truncated manifest, missing manifest, truncated `asset.bin`, manifest copied under another asset id, same-size bit rot, replace-after-skip, nonexistent directory; 2 in `CommittedAssetRecordCodecTest`). Revert-and-observe: disabling the rebuild made 10 of the 12 restart tests fail (the two that pass do so by design: in-flight-not-exposed and empty-directory); restoring it and removing only the size check, the identity check and the per-chunk digest check made exactly the truncated-file, swapped-manifest and bit-rot tests fail. Apple: `AppleFileAssetProvider`/`AppleFileAssetIo` got the same fix and a mirrored `AppleFileAssetProviderRestartTest` (12 tests); `:dataloom-assets:compileKotlinIosSimulatorArm64` and `compileTestKotlinIosSimulatorArm64` with `-Pdataloom.appleKlibCrossCompile=true` pass, but **the Apple code and its tests were never executed** (macOS CI only). Whole-build `checkKotlinAbi` passes in both the normal and `DATALOOM_ANDROID_BUILD=true` configurations. Not done: no fsync of the manifest on the JVM (`Files.move` has no portable hook), no whole-object re-hash at startup, no recovery of in-flight uploads, and the Apple scan cannot tell an unreadable `committed/` from an empty one (fails closed). See `docs/adr/ADR-0016-file-backed-asset-transfer-storage.md` D33 | `#97` file-backed provider |
