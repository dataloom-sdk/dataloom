# Fragment: gate #98, plugin certification kit (2026-10-01)

## (a) Proposed "Recently shipped" row

| 2026-10-01 | `#98` slice: `PluginCertificationKit` (`dataloom-plugin`'s own `io.dataloom.plugin.testkit` package), closing this row's own previously-named "the certification kit" gap. Matches `dataloom-assets`'s established `AssetProviderContractKit` shape exactly -- a reusable, framework-neutral class a caller builds with a `pluginFactory: (PluginManifest, PluginExecutionBounds) -> DataLoomPlugin` (and, for a host certifying its own authorizer, an `authorizedAuthorizerFactory`/`deniedAuthorizerFactory` pair with sensible built-in defaults), whose `run()` executes every scenario against the real, unmodified `PluginRegistry`/`PluginLifecycleStateTracker`/`PluginExecutionBoundsEnforcer` engine and returns a `PluginCertificationReport` a caller asserts with `assertAllPassed()`. Because `DataLoomPlugin` is a pure identity-and-bounds shape with no lifecycle callback to invoke (unlike `AssetProvider`, which has real behavioural methods the asset kit calls directly), the kit certifies a plugin implementation by driving the real engine around it rather than calling methods on it. Covers, as 15 scenarios across five categories: every edge `PluginLifecycleTransitions` documents as legal succeeds and updates tracked state, and every other ordered state pair (including same-state requests -- 38 pairs total) is structurally rejected and leaves state unchanged; dependency/version-gated activation for a dependency in range, below its declared minimum, above its declared maximum, missing (unregistered), disabled, and merely not-yet-`ACTIVE`; the execution-bounds enforcer's non-`ACTIVE`-invocation refusal, concurrency-ceiling bulkhead, and timeout cancellation; authorized-transition gating (an authorized request applies, a denied request leaves state unchanged and reports the authorizer's own reason code, and an illegal transition never consults the authorizer at all); and permission-gated activation (granted/missing declared permissions). Per this gate's own "prove the kit catches violations" discipline (the reusable-test-kit form of revert-and-observe), four deliberately-broken fakes -- one per non-trivial category -- are fed through the same kit and confirmed to fail exactly the scenario they break: a plugin that corrupts its own declared SDK-compatibility range (lifecycle), one that silently drops its own declared dependencies (dependency gating), one that ignores its own declared execution bounds (bounds enforcement), and a denied-authorizer slot filled with an authorizer that always authorizes (authorized-transition gating); all four are caught, and a conforming implementation passes the full suite. **Verified:** `:dataloom-plugin:jvmTest` -- 162 tests, 0 failures, including the 6 kit-proof tests above; `compileTestKotlinIosSimulatorArm64`/`IosX64`/`IosArm64` (cross-compiled, not executed -- no macOS host in this session); `checkKotlinAbi` passes with a purely additive diff (`PluginCertificationKit`, `PluginCertificationReport`, `PluginCertificationReport.Result`; zero deletions). **Not run against any real plugin:** confirmed directly against source (repository-wide search for `: DataLoomPlugin` implementations) that no non-trivial `DataLoomPlugin` implementation exists anywhere in this repository today beyond test fixtures (`FakePlugin`-style classes in `dataloom-plugin`'s and `dataloom-runtime`'s own test sources) -- consistent with this row's own already-documented "no application-facing plugin-registration API exists yet." The kit's own test suite is therefore the only integration proof available; a real reference plugin (a separate, already-named `#98` gap) would be the first genuine third-party-shaped user. No defect was found in existing plugin-lifecycle source while building this: every scenario's outcome matched its documented behavior exactly on the first implementation. | `#98` |
