# Fragment: gate #97, content allow/deny/scan/quarantine hooks (2026-10-01)

## (a) Proposed "Recently shipped" row

| 2026-10-01 | `#97`: content allow/deny/scan/quarantine hooks (`FR-ASSET-012`). New `AssetContentPolicy` SPI (`dataloom-assets/.../AssetContentPolicy.kt`) wired into `AssetTransferEngine` as one new, trailing, additive constructor parameter (`contentPolicy: AssetContentPolicy? = null`, `null` is the identity default -- behaviour is byte-for-byte unchanged when it is not supplied), the same shape as the engine's existing `observer`/`transforms` hooks. Evaluated once per chunk, exactly at the point this engine already holds the chunk's verified logical bytes (post-digest-verify, pre-upload on the upload side; post-decode-and-digest-verify, pre-sink-write on the download side) -- the same bounded-memory point `AssetCompressor`/`AssetChunkCipher` already operate at, so no whole-object buffering was introduced. Decision shape (`AssetContentPolicyDecision`: `Allow` / `Deny(reasonCode)` / `Quarantine(reasonCode)`) mirrors `PluginLifecycleAdministrationAuthorizationDecision`'s established convention in this codebase (a trivial allow plus bounded-reason-code refusal cases, decided inside one `suspend` call) rather than inventing a new vocabulary; confirmed by reading that type and `ConflictDetector` first -- neither has, nor does this, a "pending" third state, so a hook needing real scanning time is expected to await its own result inside `evaluate` rather than defer the decision. `Deny` and `Quarantine` both fail the session terminally with their own new `AssetErrorKind` (`CONTENT_POLICY_DENIED` / `CONTENT_POLICY_QUARANTINED`, both `ErrorCategory.POLICY`/`NON_RECOVERABLE`, surfaced through the existing `AssetTransferOutcome.Failed`/`session.failure` mechanism -- no new sealed `AssetTransferOutcome` variant was added, to avoid breaking exhaustive `when` matches in consumer code) and run exactly the cleanup every other terminal failure already runs: `provider.abortUpload` (which removes every chunk the provider committed for that session, not only the refused one -- verified, see below) or `sink.discard()`. **Verified locally (JVM, executed):** `AssetContentPolicyTest` (6 tests, commonTest) and `FileAssetProviderContentPolicyTest` (4 tests, jvmTest, checked directly against the real filesystem the same way `FileAssetProviderCleanupTest` does) all pass; the full `dataloom-assets` JVM suite is now 247 tests across 20 classes, all green, with zero regressions in the 237 pre-existing tests. **Revert-and-observe performed:** the two `enforceContentPolicy(...)` call sites in `AssetTransferEngine` were manually commented out and the suite re-run -- 9 of the 10 new tests failed as expected (the tenth is a no-policy-configured baseline test that is unaffected by the revert, by design), then the real wiring was restored and the full suite re-verified green. **Verified by cross-compilation only (Kotlin/Native, not executed -- no macOS host available):** `compileTestKotlinIosSimulatorArm64` succeeds for the shared commonTest file; no new Apple-specific test was added (the file-backed filesystem proof is JVM-only, matching `FileAssetProviderCleanupTest`'s own scope). ABI baselines (`api/dataloom-assets.api`, `api/dataloom-assets.klib.api`) were regenerated via `updateKotlinAbi -Pdataloom.appleKlibCrossCompile=true`, re-staged, and `checkKotlinAbi` passes at both module scope and whole-build scope; the diff is exactly the new public types plus the one new trailing constructor parameter, nothing else. | `#97` |
