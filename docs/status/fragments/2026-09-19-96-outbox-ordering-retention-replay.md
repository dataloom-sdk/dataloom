# Fragment: `#96` durable outbox ordering, acknowledgement retention, replay (2026-09-19)

For the lead to fold into `docs/status/market-readiness.md`. Not edited by the PR itself.

## (a) Proposed "Recently shipped" row

| 2026-09-19 | Implemented the lead's decided design for the durable operational-event outbox's two named design gaps (FR-EVENT-003 ordering, FR-EVENT-004 replay), superseding `docs/api/outbox-replay-investigation.md`'s "needs a design decision" conclusion. **Ordering:** every `DurableOperationalEventOutbox` entry is now an `OperationalEventOutboxEntry` carrying a durable, monotonically increasing per-ordering-key `sequence` (the envelope's `workflowId`, or a documented `OperationalEventOrderingKey.Global` for workflow-less envelopes; workflow keys are namespaced so a workflow named `global` cannot collide), assigned by `append` inside the same compare-and-set that persists the entry from the exact state that write is conditioned on — so two concurrent appenders, across processes too, can never persist the same sequence (the loser's compare-and-set conflicts, it reloads and takes the next). `OperationalEventOutboxState` persists per-key `sequenceHighWaterMarks` (bounded to 10,000 keys; past that, marks of keys with no retained entry are dropped lowest-first and a persisted `sequenceFloor` is raised so a dropped key can never be reassigned a used sequence) and validates on construction that sequences strictly increase per key in list order, so a corrupt payload cannot decode into a reordered stream. Gaps from removed entries are allowed; duplicates never. `entries`/`pendingEntries`/`acknowledgedEntries` and `DurableOperationalEventOutboxProcessor` present in that order. **Retention/replay:** `acknowledge` no longer hard-deletes — it stamps `acknowledgedAt` (from a now-required `clock`) and keeps a tombstone; new `acknowledgedEntries`, `pendingEntries`, and `replay(scope, id)` (`Replayed`/`AlreadyPending`/`NotFound`), which reopens a tombstone at its original position and sequence so the next processor pass presents it in order. Acknowledged history is bounded by default (`maximumRetainedAcknowledgedEntries` = 1,000, `0` = no replay window; optional `acknowledgedRetentionAge` measured from `acknowledgedAt`) and pruned deterministically inside every `append`/`acknowledge` compare-and-set (age first, then earliest `acknowledgedAt`, ties by list position); the pre-existing count/age policies now bound pending entries only. A duplicate `append` of an acknowledged id is `AlreadyAppended` with the original sequence (tombstones count for the duplicate check), so a producer retry never resurrects a processed entry. New `AlreadyAcknowledged` outcome; `Appended`/`AlreadyAppended` carry `sequence`. **Schema:** persisted schema/codec version bumped to 2 (`DurableOperationalEventOutbox.CURRENT_SCHEMA_VERSION`, referenced by the five `DataLoom*OperationalEventOutboxSpec` defaults); the codec still decodes version 1 (sequences assigned per key in list order, everything pending) and there is no other migration. `DataLoomBuilder` passes `deps.clock` to all five outbox constructions. **Verified:** `:dataloom-api:jvmTest` (969 tests, 0 failures) and `:dataloom-runtime:jvmTest` (1,826 tests, 0 failures) on Windows JVM, including 35 new outbox ordering/replay/pruning tests (a deterministic lost-race test where a second outbox instance commits between the loser's plan and its compare-and-set and the loser takes the next sequence; a 30-appender interleaved test across two outbox instances that asserts per-key sequences are exactly `1..n` and that the store really lost compare-and-set races; sequence non-reuse after acknowledgement pruning and after count eviction; bounded-tracking floor tests; state-invariant rejection), 19 codec tests including a hand-built version-1 payload and version-2 round-trip with tombstones/marks/floor, and 3 new processor tests (interleaved-workflow presentation order, ordered re-presentation of never-acknowledged `Skipped`/`Failed` entries ahead of later appends, an acknowledged entry replayed through the outbox re-presented in order). `checkKotlinAbi -Pdataloom.appleKlibCrossCompile=true` passes whole-build (JVM `.api` + iOS `.klib.api` regenerated for `dataloom-api` only; diff is exactly the new/changed outbox surface); `compileKotlinIosSimulatorArm64` and `compileTestKotlinIosSimulatorArm64` pass for `dataloom-api` and `dataloom-runtime`. **Not verified:** the Kotlin/Native (iOS Simulator) test run of the new tests (cross-compiled only; they use no wall-clock dependency, so they follow their sibling tests' `runTest` style); `RoomDurableStateStoreOperationalEventOutboxIntegrationTest` (updated for the new state shape plus one new tombstone round-trip test, but `:dataloom-queue-room` is not included in the local Windows build so it was not run — CI only); no real-store multi-process race (only in-memory stores modelling a concurrent writer). See `docs/api/outbox-replay-investigation.md` (`#96`, 2026-09-19) | `#96` feature |
