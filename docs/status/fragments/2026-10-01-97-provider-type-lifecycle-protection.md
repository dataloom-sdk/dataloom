# Fragment: gate #97, ProviderType/lifecycle for asset providers plus #94 retry/circuit protection (2026-10-01)

## (a) Proposed "Recently shipped" row

| 2026-10-01 | `#97`: `ProviderType.ASSET` and full `AssetProvider : DataLoomProvider` conformance, plus opt-in circuit-breaker/retry protection around `AssetTransferEngine`'s provider calls (`#94`). Investigated all three named sub-items in this gate's long-standing "still pending" line ("ProviderType/lifecycle for asset providers plus #94 retry/circuit and #96 events around the engine") against current `main`: the `#96` events sub-item was already fully delivered by `#96`'s own PR ([#458](https://github.com/dataloom-sdk/dataloom/pull/458), `AssetTransferOperationalEventRecorder`/`DataLoomBuilder.assetTransferOperationalEventOutboxConfiguration`) before this PR started, so it is dropped from "still pending" with no further work here; the other two were genuinely open — `AssetProvider`'s own KDoc said outright "`AssetProvider` deliberately does not extend `DataLoomProvider` in this slice... that follows in a later slice", and `AssetTransferEngine`'s own KDoc said "Retry policy (backoff, budgets, circuit breaking) belongs to the caller or to the runtime's retry engine, not to this engine" — this PR is that later slice and that caller. **Lifecycle**: added `ProviderType.ASSET`; `AssetProvider` now extends `DataLoomProvider` (`descriptor`/`initialize`/`health`/`close`), implemented trivially (no I/O) on all three concrete providers (`InMemoryAssetProvider`, JVM/Android `FileAssetProvider`, Apple `AppleFileAssetProvider`) mirroring `AndroidConnectivityProvider`'s own fixed-descriptor convention exactly. No `DataLoomBuilder` special-casing was added for this: an `AssetProvider` instance registered via the builder's existing `providers(...)`/`provider(...)` — the same opt-in every other provider type already requires — now simply participates in the existing, unmodified `ProviderLifecycleCoordinator.initialize()`/`shutdown()` loop over the registry, because it is now a `DataLoomProvider`. An `AssetProvider` supplied only to `DataLoomAssetTransferSpec` and never also registered remains un-managed, byte-for-byte the pre-existing behavior (proven by a dedicated negative-control test, and by the pre-existing `omittingAssetTransferConfigurationDoesNotChangeProviderLifecycleBehavior` test continuing to pass unchanged). **Circuit/retry**: new `DataLoomBuilder.assetProviderProtectionConfiguration(DataLoomAssetProviderProtectionSpec)` mirrors the existing `DataLoomStorageProtectionSpec`/`StorageCircuitProtectionRuntime`/`ProviderProtectionStorageBridge` pattern exactly for `AssetProvider`'s nine operations (`AssetCircuitOperation`, `AssetCircuitScopes`, `CircuitBreakerAssetOperationAdapter`, `ProtectedAssetOperations`, `AssetCircuitProtectionRuntime`, `ProviderProtectionAssetBridge`) — same reused `CircuitBreakerCoordinator`/`CircuitBreakerExecutionGate`/`CircuitBreakerProviderOperationAdapter` machinery the queue worker's and storage/transport's protected paths already use, no parallel circuit implementation. Provider-side "retry" in this codebase's existing sense (`RetryPolicy`/`SynchronizationRetryEvaluator`) is inherently a queue-reschedule concept tied to `SynchronizationResult`/`QueueEntry`, which `AssetTransferEngine` is not built on (it is a direct suspend-call engine over durable, caller-resumable sessions); genuinely reusing that machinery here would require either forcing asset transfers through the queue or inventing a parallel retry concept, so this PR scopes "retry" honestly to the circuit breaker's own retry-after-open-duration behavior (reusing `CircuitBreakerConfiguration.openDuration`) rather than adding a second, asset-specific retry evaluator — the `AssetTransferEngine` KDoc's own words, "or to the runtime's retry engine", are satisfied by the circuit breaker's existing machinery, not a new one. Opt-in: omitting `assetProviderProtectionConfiguration` leaves `DataLoomAssetTransferSpec.provider` unwrapped and behavior unchanged. A circuit rejection is surfaced to the engine as `Recoverability.RECOVERABLE` (never `NON_RECOVERABLE`) specifically so `AssetTransferEngine.onError` reports it as `AssetTransferOutcome.Interrupted` (resumable) rather than destroying an otherwise-healthy session over a transient circuit condition — a deliberate, documented divergence from the storage/transport bridges' equivalent mapping, explained in `ProviderProtectionAssetBridge`'s own KDoc. **Verified locally (JVM, executed), `dataloom-runtime:jvmTest`**: four new tests in `DataLoomBuilderAssetProviderLifecycleAndProtectionTest` — (1) a registered `AssetProvider`'s `initialize()`/`close()` are each called exactly once by `DataLoom.initialize()`/`shutdown()`; (2) the same provider supplied only to the asset-transfer spec and never registered gets zero lifecycle calls (negative control); (3) a provider whose `openUpload` always fails with a circuit-eligible, recoverable error trips a real in-memory `CircuitBreakerStateStore` at exactly its configured `failureThreshold` (2), after which a further `engine.upload()` call is rejected by the now-open circuit and never reaches the provider again (call count stays at 2, proven, not inferred); (4) the identical failing provider with protection NOT configured has every one of 3 attempts reach the provider directly (call count reaches 3) — the mandatory negative control. **Revert-and-observe discipline**: temporarily reverted the `DataLoomBuilder` wiring that passes the protected bridge to `AssetTransferEngine` and reran test (3) — it failed exactly as expected (circuit-trip assertion at line 105), proving the test is not vacuous; separately, temporarily removed the `.provider(...)` registration from test (1) and reran it — it failed exactly as expected (initialize-count assertion at line 71), proving that test is not vacuous either. Both reverts were restored before committing. Also ran the full existing `dataloom-assets:jvmTest` and `dataloom-runtime:jvmTest`/`dataloom-provider-api:jvmTest` suites (pre-existing tests, including `DataLoomBuilderAssetTransferTest`, `DataLoomBuilderProviderProtectionTest`, and the full `AssetProviderContractKit` suite against all three concrete providers) — all pass unchanged, confirming this is additive. Updated one pre-existing exhaustive-`ProviderType.entries` test (`ProviderContractsTest`) to include `ASSET`. ABI: `dataloom-provider-api`, `dataloom-assets`, and `dataloom-runtime` baselines were regenerated (`updateKotlinAbi`, both the default and `DATALOOM_ANDROID_BUILD=true` configurations, per this gate's own addendum; the `api/*.api` and `api/jvm/*.api` files are confirmed byte-identical with `cmp`), and `checkKotlinAbi` passes module-scoped in both configurations and whole-build-scoped (default configuration). Diffs contain exactly the intended surface (one new enum entry; `AssetProvider : DataLoomProvider`; three provider classes' new `descriptor`/`initialize`/`health`/`close`; the new protection types). **Not verified (no macOS host available for this task)**: Kotlin/Native (`iosArm64`/`iosSimulatorArm64`/`iosX64`) compilation of `dataloom-assets`/`dataloom-runtime` with these changes was exercised only as a byproduct of the `-Pdataloom.appleKlibCrossCompile=true` ABI tooling (which does compile those targets to produce the klib ABI dump) and succeeded, but no Apple test target was run and no simulator/device execution occurred — same standing caveat as every other Apple-side slice of this gate. | `#97` |
