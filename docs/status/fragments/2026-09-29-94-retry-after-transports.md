# Fragment: `#94` `Retry-After` / retry-pushback parity across transport adapters (2026-09-29)

For the lead to fold into `docs/status/market-readiness.md`. Not edited by the PR itself.

## (a) Proposed "Recently shipped" row

| 2026-09-29 | Closed the FR-RETRY-005 gap PR `#438`'s qualification matrix found: "Only the Ktor transport parses `Retry-After`. Retrofit, GraphQL and gRPC never produce a `RetryDelayHint`." Extracted Ktor's ad hoc numeric-seconds parser into a new shared `io.dataloom.api.error.RetryAfterParser` (`dataloom-model`), which every HTTP-based adapter now calls so they accept and reject identical input: delta-seconds and all three RFC 9110 `HTTP-date` forms (IMF-fixdate, obsolete RFC 850, asctime, including two-digit-year rollover and leap-second/leap-day handling), bounded to `[0, 24h]`, with malformed/negative/missing/multi-valued/case-varied headers producing no hint rather than a guess; an `HTTP-date` requires an injected `DataLoomClock` (never a wall-clock read) and produces no hint without one. Ktor gained the same handling on `503` it already had on `429` (RFC 9110 ties `Retry-After` to both) and an optional `clock` constructor parameter; Retrofit's `RetrofitTransportErrorMapper.Default` and the GraphQL adapter's new `protected open val clock` do the same by reading the real `okhttp3.Headers` on `HttpException.response()` and the real `List<HttpHeader>` on `ApolloHttpException.headers` respectively — both transport data the adapter already receives, not synthesized. gRPC has no `Retry-After` header, so it instead reads the standard `grpc-retry-pushback-ms` status trailer (gRPC's A6 retry design) via `io.grpc.Metadata`, scoped to `RESOURCE_EXHAUSTED`/`UNAVAILABLE` — the two codes this mapper already classifies `RECOVERABLE` — without inventing a new header or changing any status code's existing `Recoverability`; a negative pushback value (the server's explicit "do not retry") yields no hint, same as malformed input. Each adapter attaches the bounded hint via a new `RetryDelayHintCarrier` error subtype (`RetrofitTransportProvider`'s `RetrofitRetryableTransportError`, `GraphQLRetryableTransportError`, `GrpcRetryableDataLoomError`) only when a valid hint exists; otherwise the existing plain error type is returned unchanged, so every pre-existing test in all four transport modules passes unmodified. Pre-V1 ABI change to `dataloom-model` (new public `RetryAfterParser`) and `dataloom-transport-ktor` (new constructor parameter); regenerated and confirmed byte-identical between the normal and `DATALOOM_ANDROID_BUILD=true` configurations for `dataloom-model` (which has both baseline layouts); `dataloom-transport-ktor`/`dataloom-transport-graphql` (single-layout transport modules) regenerated and diffed to exactly the intended surface. 54 new table-driven tests (delta-seconds, `HTTP-date` past/future/malformed/negative/huge/missing/multiple-headers/case-insensitive-names) across `RetryAfterParserTest` (8, pure parser, plus its own table-driven cases covering dozens of individual inputs), `KtorRetryAfterTest` (12), `RetrofitRetryAfterTest` (12), `ApolloRetryAfterTest` (12), and `GrpcRetryPushbackTest` (10), each of the four transport-level suites driving the real transport's public `pushChanges`/`GrpcStatusMapper.map` path end-to-end so the hint is proven to reach `RetryDelayHintCarrier` on the adapter's own output, not just the shared parser in isolation. `:dataloom-model:jvmTest`, `:dataloom-transport-ktor:jvmTest`, `:dataloom-transport-graphql:jvmTest`, `:dataloom-transport-retrofit:test`, `:dataloom-transport-grpc:test`, and `:dataloom-runtime:jvmTest` (unmodified, confirming the runtime's existing `RetryHintEvaluator` seam is unaffected) all green; `dataloom-model`/`dataloom-transport-ktor`/`dataloom-transport-graphql` iOS main and test cross-compiled for `iosArm64`, `iosSimulatorArm64`, `iosX64`; whole-build `checkKotlinAbi` green in both configurations. Not implemented: `dataloom-transport-retrofit` and `dataloom-transport-grpc` have no ABI baseline (JVM-only, `explicitApi()`, no `api/` directory), so no baseline regeneration applies there. Not verified: any real device, Simulator, or live gRPC/GraphQL server (all tests are JVM-side mocks/in-memory exceptions; gRPC's `GrpcRetryPushbackTest` constructs `StatusException`/`StatusRuntimeException` with real `io.grpc.Metadata` trailers directly rather than through a live channel).
