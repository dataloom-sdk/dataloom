For the lead to fold into `docs/status/market-readiness.md`. Not edited by the PR itself.

## (a) Proposed "Recently shipped" row

| 2026-09-20 | Implemented decision D18 for `#95`'s loop/non-convergence gap: under fail-closed application (`Defer`/`Fail`/unresolved block the batch and leave the checkpoint unadvanced) the same batch re-conflicted on the same entity forever. New, opt-in, payload-free durable quarantine: `DurableConflictQuarantineLog` (`dataloom-api`, following `DurableUnresolvedConflictLog`) keeps a per-entity `ConflictQuarantineRecord` (status, occurrence count, first/last seen, last `ConflictId`, last selected resolver ID, quarantine time, release evidence) in any `DurableStateStore` (`ConflictQuarantineRecordCodec` + `ConflictQuarantineScope.KeyEncoder` for string-payload stores), written with a bounded load/compare-and-set loop so concurrent occurrences each land exactly once. `ConflictQuarantinePolicy` = threshold (default 5, minimum 2; the threshold-th occurrence is the one that quarantines) plus optional `windowMillis`. `SynchronizationConflictOrchestrator` (new optional `ConflictQuarantineTracker`) counts every detected conflict, including never-resolved ones, after resolver-ID selection and before lookup, and returns new `ConflictOrchestrationResult.Quarantined` (no resolver invoked) or, when the counter cannot be updated, `QuarantineUnavailable` (fail closed). `InboundConflictDecisionPreparer` blocks on both exactly like `Defer`/`Fail` (`DL-CONFLICT-QUARANTINED`, or the store error / `DL-CONFLICT-QUARANTINE-CONTENTION`): nothing applied, checkpoint not advanced. Release reuses the existing authorized path: `ConflictAdministrationCoordinator.releaseQuarantine` / `DataLoomConflictAdministration.releaseQuarantine`, authorized by the same host `ConflictAdministrationAuthorizer` through a new `authorizeQuarantineRelease` method that defaults to `Denied` (no new privilege model; authorizer runs before any state is read); release evidence is written atomically with the state change and is idempotent by command ID. Wired via `DataLoomConflictQuarantineSpec` on `DataLoomConflictDetectionSpec` (requires `resolvedConflictDecisionStore`) and `DataLoomConflictAdministrationSpec`; with neither supplied behavior is unchanged, and slice-1's selection policy is unchanged and covered alongside. Pre-V1 ABI change: `ConflictAdministrationAuthorizer` gains a default method; `SynchronizationConflictOrchestrator`, `ConflictAdministrationCoordinator`, both specs, `DataLoomConflictAdministration` and `ConflictOrchestrationStatus` gain additive members; new public types listed in the regenerated JVM and klib baselines (both `dataloom-api` layouts). 72 new tests: 35 in `dataloom-api` (table-driven threshold and window behavior, restart survival via fresh log AND fresh store over the same encoded bytes, a lost compare-and-set reloading and incrementing from the winner, 25 genuinely interleaved concurrent racers with no lost increment and retries asserted, threshold reached exactly once under 20 racers, release/idempotency, codec round trip and malformed input), 13 orchestrator, 9 release-authorization (deny-by-default, denied caller triggers no state read, replay, not-quarantined, not-configured, failure), 8 through the real `InboundPullSynchronizationPipeline` (quarantine blocks apply and checkpoint, release resumes, fail-closed on store failure/contention), 7 through `DataLoomBuilder` (a real repeated-sync loop quarantined at the threshold, default-deny then authorized release resumes application, no opt-in means never quarantined). `:dataloom-api` and `:dataloom-runtime` JVM tests green; iOS main+test cross-compiled. Not verified: any real device/Simulator or a Room/Apple-file-backed quarantine store (only in-memory and codec-backed fakes); operational-event outbox bridging of quarantine/release events is NOT implemented; a denied release is returned but not persisted. (`#95`, 2026-09-20) |
