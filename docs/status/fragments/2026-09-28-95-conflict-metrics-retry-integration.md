# Fragment: `#95` conflict metrics and retry/circuit integration (2026-09-28)

For the lead to fold into `docs/status/market-readiness.md`. Not edited by the PR itself.

## (a) Proposed "Recently shipped" row

| 2026-09-28 | Implemented decision D20 for `#95`'s "complete metrics and retry integration" gap (`docs/adr/ADR-0011-conflict-metrics-and-retry-integration.md`). **Metrics** reuse the existing retry/circuit telemetry mechanism rather than a second pipeline: `RetryCircuitTelemetrySignal` gains eight `CONFLICT_*` signals (detected, resolved, unresolved, deferred, failed, quarantined, quarantine released, resolver-selection tier hit), and `RetryCircuitTelemetryEvent`/`RetryCircuitMetricKey` gain three optional dimensions: a `ConflictResolverId`, the closed `UnresolvedConflictReason`, and the new closed `ConflictResolverSelectionTier` (entity type, workflow, tenant, global). Two opt-in decorators mirror the existing `Observed*` wrappers (exact delegate result, record afterwards, swallow telemetry failures, inert when not composed): `ObservedSynchronizationConflictOrchestrator` and `ObservedConflictAdministrationCoordinator` (`Released` only). A resolver ID is recorded only for a `Resolved` result, which requires a lookup in the immutable registry, so the label set is closed per instance; entity, change, conflict, and tenant IDs are never dimensions and no signal carries payload. The tier comes from new `ConflictResolverSelectionPolicy.matchedTier` and `ConflictOrchestrationBindings.selectedTier`, and `select`/`selectResolverId` now derive from the same code (selection behavior unchanged). **Retry integration adds no production code**: applying a resolved decision is the ordinary `applyInboundChanges` call on a reshaped batch, already circuit-protected by `ProviderProtectionStorageBridge` and retried by `SynchronizationRetryEvaluator` (conflict-engine blocks are `CONFLICT`-category, which the evaluator protects from retry); an inline retry was rejected as a layer no other storage operation has and one that would multiply queue retry budgets. This is now proven, not assumed. Pre-V1 ABI change to `dataloom-runtime` only (one enum, two wrappers, two accessors, three telemetry dimensions; the JVM and klib baselines regenerated and byte-identical between the normal and `DATALOOM_ANDROID_BUILD=true` configurations). 25 new tests: 15 table-driven metric tests (every orchestration outcome and decision kind, each of the four tiers, no-emission for `DetectorNotFound`/`NoConflict`, quarantined and quarantine-unavailable, quarantine release and its non-emission on replay/denial, and a cardinality test driving 500 distinct entities into exactly three metric keys), 3 pure tier-consistency tests, 3 real-pipeline retry/circuit proofs (retry then success with the replayed decision, exhausted attempts never writing a checkpoint, open circuit never invoking the provider yet keeping the durable decision), and 4 end-to-end tests through `DataLoomBuilder` with real circuit breakers and the production protected queued handler (retry then success, exhaustion, immediate stop on a non-recoverable failure, and open-circuit blocking followed by recovery after the open duration). Full `:dataloom-runtime:jvmTest` (2037 tests, all pre-existing tests unmodified) green; `:dataloom-runtime` iOS main and test cross-compiled for `iosArm64`, `iosSimulatorArm64`, and `iosX64`; whole-build `checkKotlinAbi` green in both configurations. Not verified: any real device or Simulator (common code, no platform surface). Not implemented: builder-assembled telemetry (the wrappers are host-composed, exactly as the retry/circuit wrappers are), gauges, a latency metric. (`#95`, 2026-09-28) |
