# Fragment: `#95` resolver selection policy precedence (2026-09-19)

For the lead to fold into `docs/status/market-readiness.md`. Not edited by the PR itself.

## (a) Proposed "Recently shipped" row

| 2026-09-19 | Implemented lead decision D11 for `#95`'s named policy-precedence gap, reversing the exact-`ConflictResolverId`-only selection invariant that `docs/api/conflict-resolver-policy-precedence-investigation.md` (two investigations, 2026-08-24/26) had documented across `ConflictResolverRegistry`, `SynchronizationConflictOrchestrator`, and `DataLoomConflictDetectionSpec` (that document is now marked superseded and carries the design summary). `ConflictOrchestrationBindings` gains an optional `resolverSelectionPolicy: ConflictResolverSelectionPolicy?` (default `null`): an immutable set of `ForEntityType`/`ForWorkflow`/`ForTenant` rules, each naming a `ConflictResolverId`. `SynchronizationConflictOrchestrator` builds a `ConflictResolverSelectionContext` from values already present on every detected conflict (the conflict's entity type, the request's workflow ID, and the request's tenant ID only when the host supplied one) and selects with strict precedence entity type > workflow > tenant > the binding's own `resolverId` as the global default; the most specific matching tier wins regardless of rule order, and a tenant rule never matches an absent tenant. Two rules for the same key in the same tier are rejected with `IllegalArgumentException` at policy construction. The chosen ID still goes through the unchanged `ConflictResolverRegistry.lookup`, so application registrations still override built-ins even when the policy selected the ID, and an unknown ID is still the existing `ResolverNotFound` outcome (not an exception, no silent fall-through to a lower tier). The policy rides inside `ConflictOrchestrationBindings`, so `DataLoomConflictDetectionSpec`/`DataLoomBuilder`/`InboundPullSynchronizationPipeline` needed no signature change; with no policy (or an empty one) behavior is unchanged. Pre-V1 ABI change: `ConflictOrchestrationBindings`' constructor/`copy`/`component3` gained the new parameter, plus new public types `ConflictResolverSelectionPolicy`, `ConflictResolverSelectionContext`, `ConflictResolverSelectionRule` (+ 3 subclasses); JVM and klib baselines regenerated. 39 new tests: 27 table-driven pure-policy tests (each tier alone, every pairwise and full-stack precedence in both rule orders, tenant absent, no-match falls to global, no policy/empty policy equals legacy, tie rejection per tier, value semantics), 9 orchestrator tests (exactly one resolver invoked for 11 tier/tenant combinations, tenant read from the real `ExecutionContext`, unknown ID -> `ResolverNotFound`, built-in vs application-override, no-policy equals legacy), and 3 end-to-end `DataLoomBuilder` tests in which one sync conflicts on two entity types, `invoice` resolved by `dataloom.builtin.server-wins` (remote applied) and `document` by `dataloom.builtin.client-wins` (remote omitted), with the per-conflict resolver ID visible in the durable resolved-decision log. Full `:dataloom-runtime:jvmTest` (1862 tests) green with all pre-existing tests unmodified; `:dataloom-runtime` iOS main+test cross-compiled for all three Apple targets. Not exercised on a real device/Simulator (common code, no platform surface). Not implemented: compound rules, wildcard matching, per-detector selection, build-time validation of policy IDs against the registry (`docs/api/conflict-resolution-strategies.md`, "Resolver selection policy"). (`#95`, 2026-09-19) |
