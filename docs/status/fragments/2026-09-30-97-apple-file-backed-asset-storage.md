# Fragment: gate #97, Apple (POSIX) file-backed asset transfer storage (2026-09-30)

## (a) Proposed "Recently shipped" row

| 2026-09-30 | `#97` slice 5 ([ADR-0016 addendum](../adr/ADR-0016-file-backed-asset-transfer-storage.md#addendum-2026-09-30-apple-ios-equivalent)): the Apple (POSIX) equivalent of slice 4's file-backed `AssetSource`/`AssetSink`/`AssetProvider` (`FR-ASSET-009`), closing the "no Apple implementation" gap that ADR-0016 left open. `AppleFileAssetSource`, `AppleFileAssetSink` (with the same `promote()`/range-tracked `read` as the JVM sink) and `AppleFileAssetProvider` live in `dataloom-assets`' `iosMain` source set, built directly on `platform.posix` (`open`/`read`/`write`/`lseek`/`rename`/`unlink`/`mkstemps`/`stat`/`opendir`+`readdir`), mirroring `dataloom-runtime`'s `AppleQueueFileIo` write-to-temp-then-rename idiom (`fsync`-before-rename, `errno`/`EINTR` handling) rather than inventing a new one — one disclosed strengthening beyond the JVM version, since `Files.move` has no portable `fsync` hook and `AppleQueueFileIo` already sets the durability bar on Apple. They pass the exact same `AssetProviderContractKit` the JVM provider does, unmodified — no JVM-specific assumption was found in it, so no parallel contract test was written and no kit change was needed. The one necessary substitution (not a compatibility gap) is `AppleFileAssetSink`'s written-range tracking: no `java.util.TreeMap` exists in Kotlin/Native's stdlib, so it uses a small sorted `MutableList<LongArray>` merged with one linear pass per write, still bounded by chunk count rather than asset size like the JVM version. **Verified locally (Windows, Kotlin/Native cross-compilation):** `compileKotlinIosArm64`/`IosSimulatorArm64`/`IosX64` and their test equivalents all succeed for the three new types plus a full `iosTest` suite reusing the shared contract kit, a cleanup suite, and a source/sink suite (mirroring the JVM `FileAssetProviderContractTest`/`FileAssetProviderCleanupTest`/`FileAssetSourceSinkTest` scenarios exactly); the pre-existing JVM test suite still passes unchanged; the Kotlin/Native ABI baseline (`api/dataloom-assets.klib.api`) was regenerated and now lists exactly the three new Apple types, the JVM baseline is untouched; a whole-repository `checkKotlinAbi` passes. **Not verified, and not verifiable from a Windows host:** actually running any new `iosTest` scenario — Kotlin/Native cross-compiles and links for all three Apple targets here, but executing the binaries needs a macOS host (Simulator or signed device run), which was not available in this session; the POSIX call sequences (`mkstemps`, `opendir`/`readdir` recursion, `utimes`, `lseek`-based random access) are type-checked and linked but have never actually executed. A macOS CI run is the first time they will. | `#97` |
